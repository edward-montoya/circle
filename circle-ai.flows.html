Circle AI · Interaction flows & the task contract

Three surfaces, one state,
and what a task must carry

How the CLI, Claude Code, and the observation app divide the work — and the two model corrections behind this revision: tasks are first-class and visible, and every task carries a goal and a way to test it.

The three surfaces who is allowed to do what

All three read and write the same state in .circle/. Only one of them may change it, and only one of them may open a gate. Everything below follows from that.

circle · the CLI

Authoritative for all domain logic, all state writes, all validation, all gate decisions, all scoring.

Every other surface is a client of this one. There is no second implementation of any rule.

never runs your app

Claude Code

Authoritative for execution — running commands, editing files, bringing the stack up, driving the app.

Writes state only by calling circle. Skills are the interface; hooks are the enforcement.

never opens a gate

circle serve · the app

Authoritative for nothing. It reads state, renders it, and offers copyable commands.

Two exceptions: it can approve a brief, and it can edit three config files.

never dispatches an agent
The one rule that resolves most questions: Claude Code can do everything except open a gate. It can generate a brief but not approve it. It can run a quality gate but not decide the gate passed. It can close a task only when a command it ran actually passed. The agent never grants itself permission.

The task contract correction: tasks were invisible and under-specified

First, a naming fix

Earlier drafts used three words for one thing — item, task, and unit. That is why tasks were hard to find in the screens. One word now:

TermMeansID shapeHas
ItemThe container a session works on. Kind: epic, task, or fixepic-31 · task-118 · fix-204brief, timeline, addenda
TaskThe unit of work. Standalone, or a child of an epic or a larger tasktask-118.1 · epic-31.4goal + verification, dependencies, state
UnitRemoved. It was a third name for a task.

A standalone task is a task with no parent — the same record, so the fix and epic flows share one code path. Hierarchical IDs follow the model the PRD already cites from beads.

Every task carries a goal and a way to test it

This is the requirement that changes the model. A task without a stated goal is a prompt; a task without a verification command closes on the agent's word. Both are now structurally impossible.

# .circle/items/tasks/task-118/tasks/task-118.3.toml
id          = "task-118.3"
parent      = "task-118"
title       = "429 body + Retry-After header"
state       = "ready"          # ready | claimed | closed | blocked
depends_on  = ["task-118.2"]

[goal]
statement = """A rate-limited client receives a 429 carrying a
Retry-After header that tells it when it may retry."""
# REQUIRED. One sentence. What "done" means for this task alone.

[verification]
kind    = "e2e"                # unit | integration | e2e | manual
gate    = "test:e2e"           # must name a gate in [quality]
command = "pnpm playwright test search/rate-limit"
expect  = "exit 0"
# REQUIRED. kind = "manual" additionally requires a justification
# and a reviewer, and counts against the machine-checkable ratio.
Two hook-enforced rules make this real — and they use the two Claude Code hooks that exist precisely for it.
  • TaskCreated → exit 2 prevents creation of a task with no goal statement, no verification, or a gate that isn't declared in the quality contract.
  • TaskCompleted → exit 2 prevents closure until an event exists showing the verification command passed after the task's most recent commit.

The consequence worth noticing: the task closure component of the status score stops being an assertion and becomes a measurement. Before, closure meant the agent marked it done. Now it means a named command exited zero after the last change. That moves 20 points of the score from "claimed" to "proven" — the same shift the change timeline made for commits.

The cost, stated plainly. Some tasks genuinely resist automated verification — a copy change, a log message, a design tweak. kind = "manual" exists for those, but it requires a written justification and a named reviewer, and it lowers the machine-checkable ratio that circle goal validate reports. That friction is deliberate: manual should be visible, not free. If it turns out most tasks land on manual in real repos, the 70% machine-checkable target is wrong and should be lowered rather than gamed.

Open for your call three things this change forces

  • Does a fix need tasks at all? The PRD calls the fix flow a “short-circuit path — no task graph.” But under this rule a fix still needs a goal and a verification, or it closes on the agent's word. Proposal: a fix is a single task whose verification is the reproduction command from circle hunt. Same rule, no graph.
  • Is manual verification allowed at all in v0.1? Forbidding it is cleaner and forces the discipline, but will make Circle unusable on repos with real copy and design work. I have kept it, with friction.
  • Does a task need its own blast radius? Today the brief declares one radius for the whole item, so a four-task item cannot express that task 1 touches src/mw/ and task 4 touches Makefile. Per-task paths would make the write-block far more precise — and would be the reason docs/api/search.md in F4 was flagged against the item instead of the task that actually touched it.
